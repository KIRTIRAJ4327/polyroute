## Technological uncertainty

1. **Can the Pareto filter operate uniformly across four heterogeneous
   axes (time, cost, effort, reliability) without a bespoke dominance
   rule per axis?**
   - Why it's uncertain: the standard Pareto formulation assumes every
     axis is commensurate and lower-is-better. Effort is a composite
     (walking distance + transfer count) and reliability is a sigma in
     minutes — neither is naturally comparable to time or cost.
   - Why routine engineering can't resolve it: the behavior under user
     preference weights is emergent — you have to implement and
     experiment to see whether dominated candidates get surfaced.

2. **Where should the rideshare / transit boundary sit in the adapter
   layer, given that Uber's ToU §II B prohibits direct third-party
   price comparison and Lyft's public API was retired in 2021?**
   - Why it's uncertain: options are (a) heuristic-only estimator,
     (b) partner API with a B2B gate, (c) no rideshare at all. The
     research in `docs/research.md` settled this, but the concrete
     adapter interface needs to reflect the legal boundary in code, not
     just in prose.

3. **Will OTP2's GraphQL `plan` schema give us enough structure to
   recover route/operator/mode reliably across TTC, GO, UP, MiWay, and
   Brampton feeds simultaneously?**
   - Why it's uncertain: OTP2 normalizes mode strings across GTFS
     feeds, but individual agencies use different `route_type` codes
     and some fields (`agency.name`) are optional per feed.

## Systematic investigation

1. **Hypothesis:** Lower-is-better normalization across all four axes,
   followed by min-max scaling per axis, produces a stable ranking when
   user weights are applied.
   - Method: implement the filter (`polyroute/core/pareto.py`), score
     hand-crafted candidates (`polyroute/adapters/mock_toronto.py`), and
     run `examples/toronto_airport.py` with `--cheap`, `--fast`,
     `--luggage` to see whether the ranking shifts meaningfully.
   - Result: ranking does shift as expected — `--fast` promotes Uber to
     rank 1, `--cheap` promotes the transit-heavy bus/subway/UP path.
     4 of 5 hand-crafted candidates ended up on the Pareto frontier,
     which is the right shape (one dominated candidate means the filter
     is actually filtering, not trivially passing everything).
   - Next step: repeat the experiment with real OTP2 output once the
     adapter is integration-tested against the Toronto container.

2. **Hypothesis:** The OTP2 response mapper can be written as a pure
   function over a captured GraphQL JSON payload, decoupling the mapper
   from HTTP transport and making it unit-testable without a live
   container.
   - Method: capture a representative response shape in
     `tests/fixtures/otp2_plan_response.json`, implement
     `_itinerary_from_otp2` as a module-level function, and assert on
     mode mapping, route/operator preservation, sigma assignment, and
     itinerary totals.
   - Result: passing. 7 unit tests run in 0.05s, no network.
   - Next step: run the live integration suite
     (`tests/integration/test_otp2_live.py`) against a real OTP2
     container once GTFS feeds are fetched — this closes the loop on
     uncertainty #3.

## Technological advancement

- Confirmed that Pareto-over-four-axes is tractable in pure Python with
  no external optimization library (`pareto_front` runs in O(n²) on the
  candidate set — fine for n < 50, which is the realistic upper bound
  for a single query).
- Confirmed that OTP2's Index GraphQL schema exposes everything needed
  to reconstruct a polyroute `Itinerary` — the mapper doesn't need to
  round-trip through OTP2's JSON routing API.
- Confirmed (via `docs/research.md`) that honest-estimate rideshare
  pricing is the only legally viable path for third-party price
  comparison. This constrains the rideshare adapter design before any
  code is written.
