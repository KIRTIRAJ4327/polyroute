## Technological uncertainty

1. **Can the Pareto filter operate uniformly across four heterogeneous
   axes (time, cost, effort, reliability) without a bespoke dominance
   rule per axis?**
   - Why it's uncertain: the standard Pareto formulation assumes every
     axis is commensurate and lower-is-better. Effort is a composite
     (walking distance + transfer count) and reliability is a sigma in
     minutes — neither is naturally comparable to time or cost.
   - Why routine engineering can't resolve it: the behavior under user
     preference weights is emergent — you have to implement and
     experiment to see whether dominated candidates get surfaced.

2. **Where should the rideshare / transit boundary sit in the adapter
   layer, given that Uber's ToU §II B prohibits direct third-party
   price comparison and Lyft's public API was retired in 2021?**
   - Why it's uncertain: options are (a) heuristic-only estimator,
     (b) partner API with a B2B gate, (c) no rideshare at all. The
     research in `docs/research.md` settled this, but the concrete
     adapter interface needs to reflect the legal boundary in code, not
     just in prose.

3. **Will OTP2's GraphQL `plan` schema give us enough structure to
   recover route/operator/mode reliably across TTC, GO, UP, MiWay, and
   Brampton feeds simultaneously?**
   - Why it's uncertain: OTP2 normalizes mode strings across GTFS
     feeds, but individual agencies use different `route_type` codes
     and some fields (`agency.name`) are optional per feed.

4. **Can a first-mile composition strategy (rideshare-to-anchor, then
   transit-the-rest) produce non-dominated candidates often enough to
   justify the fan-out cost across 5+ GTA transit anchors?**
   - Why it's uncertain: composed candidates inherit the transit leg's
     reliability sigma via independent-variance combination
     (sqrt(σ₁²+σ₂²)), which may or may not beat a direct rideshare on
     the reliability axis depending on surge and the transit frequency
     at the anchor. The Pareto frontier shape under realistic weights
     isn't obvious from theory alone.
   - Why routine engineering can't resolve it: requires running the
     four-axis Pareto filter over a set of composed + direct
     candidates and inspecting the dominated set empirically.

5. **How should graceful degradation work across a heterogeneous
   adapter set when one adapter is down but others are live?**
   - Why it's uncertain: a planner orchestrator either (a) fails the
     whole call, (b) degrades silently, or (c) surfaces partial
     results with provenance. We chose (c), but the correct semantic
     for the "mock fallback" pathway — specifically whether it stands
     in for the transit adapter, the rideshare adapter, or both —
     required iteration.

6. **Can a provider-agnostic LLM explainer fall back to rule-based
   text without leaking which path produced the output, while still
   letting the UI distinguish the two?**
   - Why it's uncertain: LLM-generated explanations vs. rule-based
     ones need to be (a) indistinguishable at the API boundary type
     level so consumers don't branch, (b) distinguishable at the
     provenance level so the UI can show "generated" vs. "static", and
     (c) cheap to fall back when the LLM call fails.

## Systematic investigation

1. **Hypothesis:** Lower-is-better normalization across all four axes,
   followed by min-max scaling per axis, produces a stable ranking when
   user weights are applied.
   - Method: implement the filter (`polyroute/core/pareto.py`), score
     hand-crafted candidates (`polyroute/adapters/mock_toronto.py`), and
     run `examples/toronto_airport.py` with `--cheap`, `--fast`,
     `--luggage` to see whether the ranking shifts meaningfully.
   - Result: ranking does shift as expected — `--fast` promotes Uber to
     rank 1, `--cheap` promotes the transit-heavy bus/subway/UP path.
     4 of 5 hand-crafted candidates ended up on the Pareto frontier,
     which is the right shape (one dominated candidate means the filter
     is actually filtering, not trivially passing everything).
   - Next step: repeat the experiment with real OTP2 output once the
     adapter is integration-tested against the Toronto container.

2. **Hypothesis:** The OTP2 response mapper can be written as a pure
   function over a captured GraphQL JSON payload, decoupling the mapper
   from HTTP transport and making it unit-testable without a live
   container.
   - Method: capture a representative response shape in
     `tests/fixtures/otp2_plan_response.json`, implement
     `_itinerary_from_otp2` as a module-level function, and assert on
     mode mapping, route/operator preservation, sigma assignment, and
     itinerary totals.
   - Result: passing. 7 unit tests run in 0.05s, no network.
   - Next step: run the live integration suite
     (`tests/integration/test_otp2_live.py`) against a real OTP2
     container once GTFS feeds are fetched — this closes the loop on
     uncertainty #3.

3. **Hypothesis:** Composition candidates (rideshare-to-anchor +
   transit-the-rest, and a walk→bike→walk variant) are expressible as
   a pure function over two `Protocol`-typed sources and a list of
   anchors, without the Planner orchestrator needing to know concrete
   adapter classes.
   - Method: write `compose_first_mile` and
     `compose_bike_share_first_mile` in `polyroute/core/compose.py`,
     typed against `TransitSource`, `RideshareEstimator`, and
     `BikeShareSource` protocols. Pin the time-continuity invariant
     (first-mile.end_time == transit.start_time) in tests. Verify
     `has_luggage` auto-skips the bike-share variant.
   - Result: passing. 12 unit tests cover both composition functions
     against `Fake*` sources, no network. Composition integrates into
     the Planner via a second `_safe()` call per variant; composed
     candidates inherit a provenance tag ("compose_first_mile" or
     "compose_bike_share_first_mile") that flows through to the API
     and UI.
   - Next step: empirical frontier analysis — measure the fraction of
     composed candidates that survive the Pareto filter on a
     real-OTP2 corpus once integration tests are live. This closes
     uncertainty #4.

4. **Hypothesis:** A Planner orchestrator can fan out to N adapters
   with per-adapter try/except isolation, stamp per-candidate
   provenance, and collapse to the empty list when every live adapter
   fails — all without adapter-specific branching in the caller.
   - Method: implement `Planner._safe(name, callable)` that swallows
     exceptions and tags successful candidates with the strategy
     name. Drive it with a test matrix covering (a) all adapters
     wired + happy path, (b) one adapter broken (`_BrokenTransit`,
     `_BrokenBikeShare`), (c) every adapter broken + fallback
     present, (d) missing adapters (None) vs. present adapters.
   - Result: passing. 16 Planner unit tests. New tests for
     per-candidate provenance pin that (a) every candidate carries
     a `source` tag, (b) the fallback pathway tags its candidates
     `"fallback"` rather than leaving them untagged.
   - Evidence the semantic choice was correct: API consumers can now
     distinguish "transit adapter returned candidates" from "mock
     fallback fired because transit was unreachable" via the
     response-level `sources[]` (wiring) and per-candidate
     `Itinerary.source` (actual producer). This addresses
     uncertainty #5.

5. **Hypothesis:** A single `LLMExplainer` interface with a
   `Callable[[str], str]` generator can front Anthropic, OpenAI, and
   Azure AI Foundry while (a) lazily importing each SDK, (b) falling
   back to the rule-based explainer on any provider error, and
   (c) stamping the output with a `source` field the UI can badge on.
   - Method: implement `ExplainResult(text, source)` where source is
     one of `"llm" | "rule-based-fallback" | "rule-based"`. Wire three
     provider factories (`anthropic_generate`, `openai_generate`,
     `azure_foundry_generate`) that each lazy-import their SDK. Drive
     the API path with a fake `LLMExplainer` in
     `tests/test_api.py::test_api_plan_uses_llm_explainer_when_set`
     and cover the fallback path with a fake that raises.
   - Result: passing. 7 new tests in `test_api.py` cover (a) rule-based
     default, (b) LLM success, (c) fallback on LLM error, (d) env-var
     driven selection for each provider including the Azure-no-
     deployment edge case. This closes uncertainty #6.
   - Next step: once a real Anthropic / Azure key is available, run
     a live integration test that measures text quality against the
     rule-based baseline on 5 representative `ScoredItinerary`
     fixtures.

## Technological advancement

- Confirmed that Pareto-over-four-axes is tractable in pure Python with
  no external optimization library (`pareto_front` runs in O(n²) on the
  candidate set — fine for n < 50, which is the realistic upper bound
  for a single query).
- Confirmed that OTP2's Index GraphQL schema exposes everything needed
  to reconstruct a polyroute `Itinerary` — the mapper doesn't need to
  round-trip through OTP2's JSON routing API.
- Confirmed (via `docs/research.md`) that honest-estimate rideshare
  pricing is the only legally viable path for third-party price
  comparison. This constrains the rideshare adapter design before any
  code is written.
- Established that `Protocol`-based dependency inversion at the
  Planner seam is sufficient to keep `core/` pure while still letting
  concrete adapters compose. Adding a new source (bike share) required
  zero changes to the orchestrator's control flow — only a new
  `Protocol` and a pair of `_safe()` calls.
- Established that the two-flavor provenance model (query-level
  `sources[]` describing wiring + per-candidate `Itinerary.source`
  describing actual producer) is sufficient to debug fan-out behavior
  from an API response alone, without adding OpenTelemetry-style
  tracing for a v0.1 deployment.
- Established that the rule-based explainer is a viable zero-
  dependency baseline for the LLM explainer, and that the
  "indistinguishable interface, distinguishable source tag" pattern
  (`ExplainResult.source`) is the right shape for future providers
  without downstream caller changes.
